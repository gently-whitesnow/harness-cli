Репозиторий для автономных агентов

Harness начинается с репозитория.

Агенту предстоит ещё тысяча итераций. Репозиторий должен оставаться понятным и пригодным для изменений.

Хорошего agent loop для этого мало. Нужны правила, которые переживут смену агента, контекста и проекта.

Какие правила я проверяю Разобраться на примерах

Я собрал в Harness CLI проверки из собственной практики: неочевидные вещи, которые приходится заново объяснять в каждом репозитории. Теперь эти правила можно одинаково применять после каждого изменения.

Подход уже прошёл много итераций; текущую версию я считаю готовой к релизу. Можно взять CLI или перенести сами правила в свой harness.

Строгость — часть идеи

Нормальное состояние — все применимые проверки включены и проходят.

Я добавляю проверку, потому что считаю её нужной. Если правило постоянно приходится отключать, для меня это повод пересмотреть правило.

Все проверки уже входят в CLI. Выбирать набор плагинов не нужно. Правила и настройки явно записаны в .harness.json и меняются вместе с кодом на ревью.

  • required нарушение блокирует прогон
  • advisory нарушение видно, но оно не блокирует
  • off проверка выключена целиком

Любую проверку можно смягчить или отключить. Спрятать отдельную находку исключением для файла нельзя.

Что включено сразу после init

Все проверки кода, структуры и правил репозитория стартуют как required. Для standalone-библиотеки стандарт архитектуры неприменим. Языки, которых в проекте нет, отмечаются как неприменимые с причиной.

Ответы о тестах, сборке и других инструментах init оставляет пустыми; соответствующие frame.* временно стоят в off. Исключение — frame.verify: путь к общему скрипту нужен сразу. Заполните ответы и включите проверки — это завершение настройки.

У архитектуры есть и рекомендательные замечания: например, плоский каталог из 20+ файлов. Они остаются неблокирующими даже при required.

              Три понятия, которые стоит разобрать

              Где лежит код. Кто от кого зависит. Как далеко тянутся связи.

              01. Слайсы: у каждой задачи своё место

              Заказы — в Orders, оплата — в Billing. Слой отвечает за роль кода, слайс — за задачу продукта. Агент находит нужную часть и меняет её в заданных границах.

              Это адаптация идей Feature-Sliced Design к .NET: разделение по смыслу, изоляция слайсов и явный публичный API. Здесь свои слои Clean Architecture и правило «слой = сборка».

              Обычный вход в слайс

              Api/Orders→Application/Orders/Contracts

              Внешний код использует объявленный API сценария. Внутреннее устройство Placement/ можно менять без обхода всех потребителей.

              Связь с соседним слайсом

              Application/Orders→Application/Billing/Contracts/X/Orders

              Billing явно открывает API для Orders. Обычный Contracts/ не разрешает импорт соседа на том же слое; нужен X/Orders, аналог @x в FSD.

              Направления слоёв и ещё несколько правил
              Разрешённые зависимости между слоями
              ОткудаКакие слои можно использовать
              HostВсе остальные — собирает приложение
              Api, ConsumersApplication, Domain
              InfrastructureApplication, Domain
              ApplicationDomain
              DomainНи один другой слой
              • Каждому Application-слайсу нужен вход в Api или Consumers. Доменные слайсы доступны верхним слоям независимо от имени слайса-потребителя.
              • Папки внутри слайса называются по назначению: Placement, Pricing. Helpers и Utils не объясняют назначение.
              • Общие зарезервированные места — Domain/Shared и Infrastructure/Persistence. Обвязка приложения живёт в Host.
              • Слой с кодом имеет одну сборку. Подключать чужие слои через Compile Include нельзя; ProjectReference подчиняется той же таблице.
              • Standalone-библиотека отмечает архитектуру как неприменимую с причиной.

              02. Цикл: зависимость вернулась к началу

              Orders использует Billing. Если Billing тоже использует Orders, модули зависят друг от друга. Их труднее менять и переносить независимо: исправление одной стороны может потребовать правок другой.

              Один из способов разорвать круг

              Orders→Billing→Domain/Orders

              Если Billing нужен только тип заказа, вынесите само бизнес-понятие в Domain. Обратная ссылка на сценарии Orders исчезнет: Domain не зависит от верхних слоёв.

              Если модули всегда меняются вместе, стоит проверить, не одна ли это задача. Добавление Contracts само по себе цикл не разрывает.

              В dependencies.csharp модуль определяется по namespace. Блокируются только связи, доказанные ридером исходников; предположение по имени не становится нарушением. Как определяется доказанная связь →

              03. Mean reach: сколько файлов видно по цепочке зависимостей

              Циклов может не быть, а связей — слишком много. Mean reach показывает, до скольких файлов в среднем можно дойти из одного файла, следуя его зависимостям. Сам исходный файл тоже считается.

              Как читать число

              Чем оно выше, тем дальше в среднем тянутся зависимости файла. Это сигнал о связанности кода, а не обещание, что при следующей задаче придётся изменить ровно столько файлов.

              Core size — размер крупнейшей группы файлов, из каждого из которых можно добраться до всех остальных. В цепочке слева такой группы нет: core size = 0.

              По умолчанию complexity.csharp требует mean reach ≤ 8 и core size = 0. При превышении отчёт называет файлы с наибольшим числом достижимых зависимостей или участников ядра.

              Что входит в расчёт и откуда предел 8

              Измеряются файлы продукта и доказанные связи между ними. Для sliced-dotnet это файлы внутри архитектурных зон; без зон — файлы вне тестовых проектов. Generated-код исключён. Host входит в число, но не в список кандидатов на сокращение связей.

              Предел 8 взят из практических замеров и устройства sliced-dotnet. Это выбранное автором ограничение, которое можно пересмотреть, накопив опыт. Оба предела явно записаны в settings."complexity.csharp".

              Установить Harness CLI и включить в работу

              Standalone-бинарь; для работы нужен Git. .NET runtime не требуется.

              1. Установите CLI: 
                curl -fsSL https://raw.githubusercontent.com/gently-whitesnow/harness-cli/master/install.sh | sh
              2. В корне репозитория создайте конфигурацию: 
                harness init --kind application

                Для standalone-библиотеки: --kind library.

              3. Заполните ответы в .harness.json, отметьте неприменимые языки и включите проверки ответов. Добавьте конфигурацию и файлы проекта в индекс Git.
              4. Подготовьте клон и проверьте репозиторий: 
                harness setup
harness check

              После каждой правки

              Включите harness check в свой verify-скрипт вместе с тестами, сборкой и линтерами. Запускайте этот скрипт в CI и возвращайте отчёт агенту для исправления.

              Harness видит только файлы в индексе Git. Сам тесты и сборку не запускает.

              0 — блокирующие проверки прошли; замечания и пробелы в готовности ещё возможны.
              1 — доказано нарушение.
              2 — проверка не завершилась достоверно.

              Объяснение правила: harness explain <check-id>.
              Обновление контракта репозитория: harness upgrade.
