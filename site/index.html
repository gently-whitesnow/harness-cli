Что ловит

То, что не поймают тесты, линтер и код-ревью на бегу

Циклы модулей

Цикл между модулями, доказанный по коду, блокирует прогон. Вложенный модуль — содержание, а не цикл.

Потолок связанности

DSM по продукту: сколько файлов затронет изменение и как велико ядро. Потолок объявлен в settings рядом с остальными, дефолт 8.0 файла и ядро 0.

Повторы между файлами

Одинаковая лексическая форма в разных файлах — находка, а не подозрение. Порог задаётся в settings.

Форма sliced-dotnet

FSD для .NET: слои × слайсы прямо в файловой системе, слой = сборка, API слайса — Contracts/, кросс-импорт — явный X/. Стандарт.

Подавления warnings

Адресные pragma, SuppressMessage, NoWarn и severity = none блокируются. Выключение правила для всего репозитория лишь печатается.

Коммиты и документация

Шаблон сообщения и commit-msg hook на весь клон. AGENTS.md не длиннее 150 строк, прочий Markdown — нарушение.

Стандарт sliced-dotnet/1 · FSD для .NET

Слои Clean Architecture × сквозные слайсы. Словарь зафиксирован, карта — само дерево

sliced-dotnet переносит на .NET то, что делает Feature-Sliced Design для фронтенда: словарь слоёв и правила импортов задаёт методология, а не репозиторий. Поэтому в .harness.json нет деклараций слоёв и модулей — только имя стандарта. Проверка читает tracked-дерево и C#-граф и уже знает, что является нарушением. Ослабить инвариант правкой конфига нельзя: форму меняет только код.

Подходит: приложение

Сервис, CLI, воркер, BFF — всё, у чего есть вход и use-cases. Один стандарт на все .NET-приложения.

"architecture": { "standard": "sliced-dotnet/1" }

Не подходит: standalone-библиотека

У библиотеки одна capability — она сама: ось слайсов вырождается, публичную поверхность держит компилятор. Стандарт дал бы только церемонию.

"architecture": { "applicable": false, "reason": "standalone library" }

1

Слой

Шесть каталогов в корне зоны: Host, Api, Consumers, Application, Domain, Infrastructure. Каждый — собственная сборка, направление рёбер держит компилятор. Обязательны Host, Application и хотя бы один вход. Чужое имя в корне зоны — нарушение, похожее — опечатка.

2

Слайс

Бизнес-capability, проходящая сквозь слои: Application/Orders и его зеркала в Api, Consumers, Infrastructure и Domain. Слайсы одного слоя друг друга не видят. Группа — один уровень <Слой>/<Группа>/<Слайс> без файлов. В корне слайсового слоя лежат только слайсы: промежуточного каталога нет, сквозной обвязке место в Host или в слайсе.

3

Сегмент

Каталог внутри слайса, названный по назначению: Placement, Pricing, а не Services или Helpers. Два сегмента зарезервированы стандартом: Contracts/ — публичный API слайса, Contracts/X/<Потребитель> — cross-API для одного названного слайса. Contracts/ живёт внутри слайса: тот же каталог в корне слоя — публичный API слоя, которого в стандарте нет, и он блокируется как no-layer-public-api.

Четыре правила импортов
  1. Только вниз по таблице. Ребро классифицируется парой слоёв автора и адресата; пары нет в таблице — нарушение. Между зонами монорепозитория рёбер нет вовсе.
  2. Слайс закрыт своим Contracts/. Всё, что входит в Application-слайс снаружи, указывает в контракт; обход внутрь запрещён. Исключение одно — Host связывает контракты с реализациями.
  3. Между слайсами — только через X/. Слайс A публикует API для B в Contracts/X/B/ (в Domain — Domain/A/X/B/), импортировать его вправе только B. Это @x из FSD 2.1: граф кросс-зависимостей виден в дереве. Порядок решений тот же — слить слайсы, спустить общее в Domain, cross-API последним.
  4. Domain читают все. Верхние слои компонуют любые Domain-слайсы, не только своё зеркало: агрегирующий read model собирает несколько доменных моделей без копий в контрактах.

Рёбра берутся из лексического C#-графа по tracked-исходникам; блокируют только Proven-рёбра. Слой = сборка: ровно один .csproj на слой с кодом, Compile Include чужого слоя — linked-компиляция и нарушение, ProjectReference — по той же таблице.

Zero-config

Карта архитектуры одинакова во всех сервисах. Агент или новый человек ориентируется в любом репозитории стандарта без чтения деклараций.

Изменить форму можно только кодом

Нет декларации — нет «осознанной правки» через ревью, которая ослабляет инвариант. Перенос каталога виден в diff как перенос каталога.

Границы держит компилятор

Слой — сборка: недопустимая ссылка не компилируется, internal действует на границе слоя, ProjectReference-граф читается как таблица.

Постепенное внедрение

Пока раскладка не совпала со стандартом, проверка идёт advisory: находки видны, гейт зелёный. Одна строка policy переводит её в required.

Что именно блокирует, а что только печатаетинварианты и конвенции проверки architecture.sliced-dotnet

Blocking при required, без адресных исключений

  • Ребро вне таблицы слоёв; ребро между зонами.
  • Ребро между слайсами одного слоя, включая их обычные Contracts/; импорт X/B/ кем-то кроме B.
  • Обход Contracts/ Application-слайса извне (кроме Host).
  • Contracts/ в корне слайсового слоя — no-layer-public-api: публичный API публикует слайс, не слой.
  • Каталог в корне слайсового слоя, который не слайс и не зарезервирован (Domain/Shared, Infrastructure/Persistence): essence-имя — no-segments-on-sliced-layers, любое другое — orphan-slice-mirror. Файл прямо в корне слоя — outside-slice.
  • Слайс без зеркала ни в Api, ни в Consumers; зеркало без слайса в Application; пустой слайс, группа или слой.
  • Каталог в корне зоны вне словаря слоёв; опечатка в имени слоя.
  • Сегмент слайса или Host по виду кода: Services, Helpers, Utils, Common, Managers, Repositories и словарь Steiger целиком; essence-имя листа в группе слайсов.
  • Слой с кодом без своего .csproj или с двумя; Compile Include за пределы слоя; ProjectReference вне таблицы; проект вне канонического слоя.
  • Цикл модулей по Proven-рёбрам.

Advisory-observations при любой policy, код возврата не меняют

  • flat-directory-grouping — каталог с 20+ authored .cs прямо в нём.
  • mutual-cross-api — два слайса публикуют X-контракты друг для друга: слить или спустить общее в Domain.
  • cross-api-fan-in — X-контракты слайса читают 4+ потребителя: слайс ведёт себя как нижний слой.
  • directories-by-purpose — essence-имя каталога на любой глубине вне сегментных позиций.
  • repetitive-naming — все слайсы слоя лежат в единственной группе: имя группы повторяется на каждом слайсе и не сообщает ничего.
  • ambiguous-slice-names — сегмент назван как свой слайс (Orders/Orders): имя не говорит о назначении.
  • insignificant-slice — слайс без ссылок из собственных входных зеркал; разнобой числа в именах; 20+ слайсов без групп.

Глубже

Связанность, циклы, DSM и повторы: как это считается и почему именно так

Все структурные проверки питаются одним графом, построенным по tracked-исходникам лексическим ридером на BCL — без Roslyn, без build output, без запуска toolchain. Это осознанная цена NativeAOT-инварианта: инструмент измеряет меньше, чем компилятор, но никогда не завышает связанность на доказанных рёбрах. Каждый блок ниже раскрывается; диаграммы интерактивны — рёбра и узлы можно двигать, чтобы увидеть, как меняется вердикт.

Граф зависимостей и уровни доказательности

Типы, объявленные в репозитории, образуют замкнутый словарь. Каждое имя в исходнике резолвится в объявление в том же порядке, что использует C#: свой namespace, затем объемлющие, затем импорты файла. Имя, не совпавшее ни с одним объявлением, — внешний импорт, а не догадка; имя с несколькими кандидатами — unresolved и в граф не попадает. Доля резолва печатается в отчёте.

Каждое ребро несёт оценку EvidenceGrade:

  • Proven — имя стоит там, где язык не допускает ничего, кроме типа: new, base list, тип параметра, поля, свойства или возврата, generic-аргумент, атрибут, typeof, sizeof, default, catch, либо тип, за которым следует вводимое им имя.
  • Inferred — имя совпало, но позиция ничего не доказывает: member access, аргумент, локальная переменная, приведение.

Blocking-находка строится только из Proven-рёбер. Тот же Proven-граф питает циклы модулей, инварианты sliced-dotnet и DSM-пределы. Всё, что связывает компилятор — extension-методы, var, перегрузки, DI, рефлексия, — невидимо; связанность занижена, никогда не завышена.

Граница модуля. Имя модуля вложено в имя объемлющего: ссылка из Shop.Orders в Shop.Orders.Contracts — содержание, а не зависимость. Ребро поднимается до первого сегмента, которым имена расходятся: Shop.Orders.Api → Shop.Billing.Core записывается как Shop.Orders → Shop.Billing.

ADR-0021 ADR-0009
Циклы модулей: единственная dependency-находка

Модули, зависящие друг от друга, нельзя упорядочить, вынести или переиспользовать в одном направлении. Это универсальный структурный дефект, который харнес умеет доказать по tracked-исходнику. Проверка становится blocking, только если выполнены сразу пять условий: детерминизм, actionable-находка, скорость, низкий риск false positive и негативная фикстура. Цикл по Proven-рёбрам проходит все пять.

Формула. Рёбра между типами схлопываются до рёбер между модулями (namespace), внутренние ссылки отбрасываются. Над графом модулей идёт алгоритм Тарьяна — итеративный, чтобы глубокий граф не съел стек. Каждая сильно связная компонента из двух и более узлов — цикл.

Что печатается. Компонента из одиннадцати модулей правдива и неисполнима; кольцо из двух — исполнимо. Поэтому внутри компоненты ищется кратчайшее кольцо (BFS от каждого узла) и печатаются строки исходника, которые его замыкают. Ребро-представитель выбирается по самой ранней локации, чтобы отчёт не менялся между прогонами.

Почему нет fan-in/fan-out. Пилот показал, что верх outgoing count закономерно занимают integration-тесты и composition roots, а высокий incoming count часто отмечает правильно выбранную стабильную абстракцию. У таких чисел нет универсального remediation, поэтому начиная с 1.5 они удалены; у цикла оно есть.

ADR-0002 ADR-0021 ADR-0029
DSM-сложность: mean reach и core size под объявленным потолком

Счётчик зависимостей описывает один файл. Design structure matrix описывает, как изменение распространяется по продукту целиком. Две метрики DSM-семейства сравниваются с потолком, который рамка объявляет в settings.complexity.csharp: meanReach и coreSize. Дефолт контракта, который пишет harness init, — 8.0 файла и 0, значения sliced-dotnet/1. Отдельного файла и команды, двигающей число, нет: потолок правится тем же reviewable-диффом, что и остальные settings.

Mean reach — ограничиваемая величина. Пусть N — число измеренных файлов, R(i) — сам файл i плюс всё, что транзитивно достижимо из него по Proven-рёбрам.

mean reach = Σ|R(i)| / N

Это абсолютное число файлов, до которых доходит изменение типичного файла. Propagation cost (MacCormack, Rusnak, Baldwin, 2006) печатается рядом как справка для сравнения с литературой: Linux 5.16 %, Mozilla 17.35 % до редизайна и 2.78 % после.

propagation cost = 100 · Σ|R(i)| / N²

Почему не propagation cost. Знаменатель N² вознаграждал дробление и наказывал удаление: за неделю нарезки на слайсы в пилоте достижимых пар стало на 13 % больше, а cost упал на 14 %, потому что файлов стало на 15 % больше. Удаление изолированного файла всегда повышало cost. Mean reach от листьев не худеет и от удаления сдвигается не больше чем на долю файла.

Core size — размер крупнейшей циклической группы файлов (Baldwin, MacCormack, Rusnak, 2014). У файлов ядра ~3× плотность дефектов; ациклический граф даёт ядро 0.

core size = max |SCC| при |SCC| > 1

Область. Измеряются только файлы внутри архитектурных зон sliced-dotnet — тесты, тулинг и сэмплы вне зоны не входят. В пилоте тесты давали 21 % файлов и 56 % достижимых пар, а подсказки указывали на Mongo-фикстуру, а не на архитектуру. Граница читается из дерева, поэтому ни ответ рамки, ни список исключений не могут перенести файл через неё. Без зоны — в монолите или standalone-библиотеке — продуктом считаются файлы вне tracked тестовых проектов: Microsoft.NET.Test.Sdk, xunit, NUnit, MSTest, TUnit, IsTestProject в собственном .csproj. Читается только XML проекта, без MSBuild evaluation; строка scope: в отчёте называет вынесенные проекты. Целиком измеряется лишь репозиторий без единого тестового проекта.

Почему предел — константа. Под sliced-dotnet файл видит свой слайс и слои под ним, а весь продукт видит только composition root в Host. Поэтому mean reach ≈ средняя достижимость внутри слайса + число файлов, видящих всё, и ни одно слагаемое не растёт с числом слайсов: многослайсовый пилот на 500 файлах даёт 7.0 файла. Tracked ratchet-бюджет агенты поднимали под каждую фичу ровно до текущего замера — отдельный файл с одним числом правился как рутина. Теперь потолок стоит среди settings рамки, и его правка — пересмотр контракта на ревью, а не budget bump. При превышении отчёт называет файлы вне Host с наибольшей |R(i)|: резать надо их исходящие рёбра.

Вычисление. SCC-конденсация — DAG; достижимость считается битовыми наборами в обратном топологическом порядке, без рекурсии и внешних зависимостей.

ADR-0032 ADR-0042 ADR-0048 ADR-0052 MacCormack 2006
Дупликация: одинаковая лексическая форма в разных файлах

Одна и та же структура, выписанная в нескольких файлах, — самый дешёвый наблюдаемый признак того, что абстракция отсутствует или была скопирована вместо вызова. Проверка находит место и останавливается: лексическое совпадение — повод открыть два места, а не доказательство, что они значат одно и то же.

Нормализация. Каждый файл сводится к коду: комментарии, содержимое строк и символов, директивы препроцессора заменяются пробелами. Остаток превращается в последовательность токенов на каждую физическую строку по этим правилам и никаким другим:

комментарий, директиваничего
строковый литералодин токен ", что бы ни было внутри
символьный литералодин токен '
числоодин токен #
ключевое слово C#само себя — if и while никогда не совпадут
любое другое словоn — все идентификаторы читаются одинаково
прочий символсам себя
пробелы, пустая строкане выживают: переформатирование не влияет на совпадение

Единица сравнения — окно из windowLines подряд идущих нормализованных строк, несущее не меньше minimumTokens токенов. Окна ниже порога не сравниваются вовсе: строки из скобок и return одинаковы в каждом файле, и их никто не вынесет. Найденная группа растёт построчно назад и вперёд, пока все вхождения согласны, и репортится один раз как целый регион. Рост останавливается на строках, уже занятых другим повтором, — ни одна строка не отчитывается дважды. Повтор внутри одного файла не репортится.

Почему 30/90 и почему required. Ретроспектива на трёх репозиториях (1085 tracked .cs): профиль 8/24 дал 354 группы, 24/72 — 14, 30/90 — одну, 36/108 — ни одной. На пилотах 30/90 нашёл 12 и 6 пар до целевого рефакторинга и ни одной после; подъём окна до 36 скрыл бы пять из 18 подтверждённых случаев. Размер окна остаётся главным фильтром шума, а minimumTokens в диапазоне 72–150 почти не влиял. С 2.9.0 harness init пишет required; существующая явная policy при upgrade не переписывается.

Возможный вред. Извлечение общего хелпера из двух блоков, которые лишь выглядят похоже, связывает то, что не должно меняться вместе. Совпадение, не пережившее чтения, лечится настройкой детектора или advisory-policy, а не принудительной абстракцией. Архитектурный инвариант, циклы и DSM-пределы независимо не дают лечить повтор общим модулем с неверным направлением зависимости.

Запуск

Установка, команды, CI

Скрипт определяет платформу, сверяет sha256 и кладёт бинарь в ~/.local/bin/harness без sudo и без .NET runtime. Той же командой харнес обновляется: пинить при установке нечего, потому что поведение задаёт проверяемый репозиторий, а не бинарь. Внутри репозитория с .harness.json скрипт заодно выполняет harness setup.

Команды
  • harness init --kind applicationсоздать явную рамку и .editorconfig
  • harness check [--verbose] [--all]проверить репозиторий; --only / --skip по id или группе
  • harness explain <check-id>смысл, формула, пределы и исправление проверки
  • harness upgrade [--dry-run]поднять pin и напечатать маршрут миграции
  • harness setupактивировать commit-шаблон и commit-msg hook в клоне
  • harness commits check a..bпроверить диапазон сообщений для CI
