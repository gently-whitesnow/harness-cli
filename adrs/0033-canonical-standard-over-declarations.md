# ADR-0033. Канонический стандарт вместо деклараций: sliced-dotnet

Статус: принят. Дата: 2026-08-27. Уточняет ярус 1
[ADR-0032](0032-topology-over-thresholds.md) до начала его реализации.

## Контекст

ADR-0032 взял у FSD механизм — форму дерева, публичные API слайсов, импорты только
вниз, — но оставил словарь на усмотрение репозитория: секция `architecture` декларирует
собственные `layers`, `modules` и `mirrors` (модель deptrac/Tach/import-linter). Сила
FSD в обратном: словарь зафиксирован методологией (семь слоёв, известные сегменты),
поэтому линтер Steiger работает без конфигурации — он читает файловую систему и уже
знает, что является нарушением. Per-repo декларации возвращают точку гибкости, которую
0032 сам назвал угрозой: осознанная правка декларации — легальный способ ослабить
инвариант, и каждый репозиторий несёт собственную карту, которую нужно писать, ревьюить
и поддерживать в актуальном состоянии.

Обсуждение с владельцем зафиксировало рамку: Clean Architecture сохраняется как
горизонтальная ось; вертикальные слайсы проходят сквозь все слои (сквозная вертикаль —
это `mirrors` из 0032, но фиксированные стандартом, а не объявляемые); стандарт един
для всех .NET-приложений — сервисов, CLI, воркеров; асинхронный вход — очереди,
подписки, фоновые планировщики — выделяется слоем `Consumers`; развивается один пресет, escape hatch в виде ручных деклараций не вводится.

Прямой перенос слоёв FSD невозможен — они UI-центричны (`pages`, `widgets`). Из 22
правил Steiger на бэкенд переносятся ~15: запреты импортов вверх и кросс-импортов,
обход публичного API, осиротевшие и пустые слайсы, опечатки в именах слоёв,
generic-сегменты; не переносятся `import-locality` (в C# нет относительных импортов)
и `no-processes`.

Standalone-библиотеки из области стандарта исключены: у библиотеки одна
capability — она сама, ось слайсов вырождается; публичную поверхность держит компилятор
(`public`/`internal` на границе assembly); входного слоя нет. Стандарт производил бы
для неё только церемонию — библиотеки покрыты ярусами 2–3 (DSM-бюджеты форме дерева
безразличны).

## Решение

Секция `architecture` контракта 2.0 сводится к выбору из двух форм:

```jsonc
"architecture": { "standard": "sliced-dotnet/1" }
// либо для standalone-библиотеки:
"architecture": { "applicable": false, "reason": "standalone library" }
```

Деклараций `layers`, `modules`, `mirrors` не существует. Карта архитектуры — сама
файловая система; харнесс печатает обнаруженные зоны, слои и слайсы в отчёте.

### Стандарт sliced-dotnet, версия 1

**Зона** — каталог, содержащий канонические слои; обнаруживается по наличию
`Application/`. Монорепозиторий может содержать несколько зон; рёбра между зонами
запрещены.

**Слои** — фиксированный словарь каталогов в корне зоны, DAG рёбер задан стандартом:

| Слой | Назначение | Разрешённые рёбра |
| --- | --- | --- |
| `Host` | composition root: Program, DI-wiring, конфигурация | во все слои |
| `Api` | синхронный вход: controllers, endpoints, команды CLI | `Application`, `Shared` |
| `Consumers` | асинхронный вход: обработчики очередей, подписок и фоновые планировщики (hosted jobs) | `Application`, `Shared` |
| `Application` | use-cases; слайсы в `Features/` | `Domain`, `Shared` |
| `Domain` | бизнес-сущности; слайсы в корне слоя, `Shared` зарезервирован | `Shared` |
| `Infrastructure` | адаптеры; слайсы в `Features/`, `Persistence` зарезервирован | `Application` (только `Contracts/`), `Domain`, `Shared` |
| `Shared` | kernel, утилиты | — |

Обязательны `Host`, `Application` и хотя бы один входной слой (`Api` или `Consumers`);
остальные опциональны, но присутствующий слой обязан быть непустым. Каталог в корне
зоны вне словаря — нарушение; близкое к каноническому имя репортится как опечатка.

**Слайсы.** Источник истины — `Application/Features/<Слайс>`. Группа слайсов —
`Features/<Группа>/<Слайс>`: один уровень вложенности, группа не содержит файлов.
Зеркала слайса: `Api/Features/<Слайс>`, `Consumers/Features/<Слайс>`,
`Infrastructure/Features/<Слайс>`, `Domain/<Слайс>`.

**Инварианты** (blocking, неподавляемые, по Proven-рёбрам ADR-0021):

1. **DAG слоёв** — каждое ребро классифицируется парой слоёв автора и адресата; пара
   вне таблицы — нарушение. Единственное широкое исключение встроено в стандарт:
   `Infrastructure/Persistence` видит `Domain/*` целиком (DbContext знает все сущности).
2. **Изоляция слайсов** — ребро между разными слайсами внутри одного слоя запрещено,
   включая их `Contracts/`, с одним явным исключением — cross-API (перенос
   стандартизованной в FSD 2.1 нотации `@x`). Слайс A публикует API для конкретного
   потребителя B в каталоге `Contracts/X/B/` (в `Domain`, где `Contracts/` нет, —
   `Domain/A/X/B/`); файлы под `X/B/` разрешено импортировать только слайсу B.
   Читается как «A пересечение с B»: граф кросс-зависимостей буквально виден в дереве
   каталогов и не требует деклараций. Приоритет решений — как в FSD: сначала слить
   слайсы или спустить общее вниз (`Domain`, `Shared`), cross-API — последнее
   средство, оставляющее связь явной и ревьюируемой.
3. **Domain — общий словарь** — верхние слои (`Api`, `Consumers`, `Application`,
   `Infrastructure`) читают любой `Domain`-слайс, не только собственное зеркало:
   `Domain` играет роль слоя entities FSD, чьи слайсы свободно компонуются сверху
   (агрегирующий read model встраивает модели нескольких доменных слайсов). Изоляция
   слайсов действует внутри самого `Domain` — там кросс только через `X/`.
4. **Публичный API** — ребро, пересекающее границу Application-слайса извне, указывает
   только в его `Contracts/`: зеркала и остальной код видят слайс через контракт, обход
   внутрь запрещён (модель `no-public-api-sidestep`). Исключение — `Host`: composition
   root связывает контракты с реализациями.
5. **Зеркальность** — слайс обязан иметь зеркало хотя бы в одном входном слое; зеркало
   без слайса в `Application` («осиротевшее зеркало») — нарушение; пустой слайс, группа
   или слой — нарушение. Это замена «мёртвой декларации» 0032: деклараций больше нет,
   но мёртвая форма остаётся видимой.
6. **Циклы модулей** — blocking, как в ADR-0032.

**Конвенции** (advisory по ADR-0002/0006, пока не накоплены негативные фикстуры):
generic-каталоги внутри слайса (`Services`, `Helpers`, `Managers`, `Utils`, `Common`);
бизнес-логика в `Host`; слайс без ссылок из собственных входных зеркал; разнобой
единственного и множественного числа в именах слайсов; переизбыток слайсов без групп.

Ярус 2 (DSM-бюджеты) и ярус 3 (детерминированные policy) не меняются.

### Что уточняется в ADR-0032

`layers`, `modules`, `mirrors` как декларации не реализуются — их роль исполняет
стандарт. `dependsOn` не существует: кросс-слайс либо запрещён, либо явен в дереве
через `X/<Потребитель>`. `publicApi` зафиксирован как `Contracts/`. Проверка «мёртвая декларация — ошибка» вырождается в
«пустая форма — ошибка». Остальное — ярусы, бюджеты, неподавляемость, NativeAOT-счёт
по лексическому графу — действует без изменений.

## Последствия

- Zero-config: `.harness.json` перестаёт быть картой архитектуры — карта совпадает с
  файловой системой, одинаковой во всех репозиториях стандарта. Агент, знающий
  стандарт, ориентируется в любом сервисе без чтения деклараций.
- Точка гибкости, оставшаяся в 0032 (осознанная правка декларации через ревью),
  закрыта: изменить форму можно только изменив код.
- Миграция services-platform превращается из написания деклараций в физическую
  реструктуризацию каталогов — дороже разово, но результат единообразен.
- harness-cli сам подпадает под стандарт (CLI — приложение, не библиотека) и мигрирует
  `src/Harness` вместе с первой проверкой формы, чтобы собственный гейт не оставался
  красным между задачами.
- Стандарт живёт в этом ADR (ADR-0010 запрещает прочий tracked Markdown); публичная
  спецификация уровня fsd.how — будущая работа, если стандарт пойдёт за пределы
  наших репозиториев.
- Риск: словарь v1 может не покрыть реальные раскладки (gRPC, BFF, background jobs
  вне очередей). Пересмотр — новым ADR и версией `sliced-dotnet/2` в имени стандарта:
  переход всегда явный, тихой эволюции словаря нет.
