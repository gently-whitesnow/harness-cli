# ADR-0004: План исполнения выводится из Git-evidence, а не из конфигурации

## Status

Partially superseded by [ADR-0011](0011-the-harness-does-not-run-the-repository-toolchain.md).
Исполнения больше нет, поэтому выведение плана исполнения потеряло предмет. Утверждение о
том, что факты берутся только из Git-tracked evidence и что окружение вызывающего не
является evidence репозитория, продолжает действовать. Отложенный здесь манифест заведён
в [ADR-0012](0012-declaration-with-an-address-of-proof.md).

## Context

Пользователь выбрал zero-config `check` для первой итерации: scripts должны жить в CLI, а
manifest появится позже только там, где convention не хватает. Первым workload служит
`services-platform`, поэтому v0 начинает со стандартной evidence его стеков — solution и
projects для .NET, manifest, scripts и lockfile для web — и оставляет расширение открытым.

Tracked manifest харнеса мог бы быть воспроизводимым источником намерения; он не отвергнут,
а отложен ради меньшего v0. Окружение вызывающего таким источником не является: наличие
глобального `pnpm`, `npm` или SDK не говорит, чем сам репозиторий фиксировал зависимости и
какие команды он объявил. Поэтому до manifest остаётся только уже tracked evidence проекта.

## Decision

План выводится только из Git-tracked evidence: lockfile называет пакетный менеджер,
`package.json` — доступные скрипты и зависимости, solution и csproj — .NET-таргеты.
Объявление `packageManager` в манифесте — тоже evidence и обязано совпадать с lockfile.

Evidence, не выделяющая ровно один план, даёт `Incomplete`, а не выбор: два корневых
манифеста, два lockfile разных менеджеров, `packageManager` против lockfile, нечитаемый
манифест. Корневой `package.json` считается собственным заявлением репозитория и имеет
приоритет над членом workspace.

## Consequences

### Positive

- Репозиторий проверяется одинаково у человека, у агента и в CI.
- Неоднозначность видна как неоднозначность и адресована репозиторию, а не скрыта выбором
  по умолчанию.
- План не требует копировать runner scripts или добавлять harness-specific config в первый
  проверяемый репозиторий.

### Negative / Risks

- Монорепо без корневого манифеста и с несколькими `package.json` не проверяется совсем:
  на services-platform план нашёлся только потому, что `apps/web/package.json` — единственный.
- Список распознаваемых lockfile (`npm`, `pnpm`, `yarn`, `bun`) живёт в харнесе; менеджер
  вне списка делает surface неоднозначным.
- Custom command, intentional exception или невыводимая граница модулей не помещаются в эту
  модель. Для них понадобится отложенный manifest; до него харнес обязан вернуть gap или
  incomplete, а не угадывать.
