# ADR-0048: Граница продукта для DSM без архитектурной зоны

## Status

Accepted. Уточняет пункт 1 [ADR-0042](0042-dsm-over-the-product-in-files.md); формулы и
область внутри зон sliced-dotnet не меняются. Бюджет, упомянутый в пунктах 4 и 5, заменён
константами [ADR-0052](0052-dsm-limits-are-constants-of-the-standard.md).

## Context

ADR-0042 вывел тесты из DSM, но только через архитектурные зоны `sliced-dotnet/1`.
Репозиторий без зоны — standalone-библиотека или backend с другой раскладкой — измерялся
целиком вместе с тестами. Владелец спросил, можно ли считать mean reach для репозитория,
не привязанного к стандарту топологии харнеса, и предложил два варианта: путь к
бизнес-логике в конфиге и флаг включения тестов с дефолтом `false`.

Прогон бинаря 2.9 по копиям двух пилотных репозиториев показал цену обоих режимов.
Область «зона» дала mean reach 10.30 и 7.04 файла; тот же код, измеренный целиком с
тестами, — 12.85 и 12.51; только слой `Application` — 3.76 и 4.36. Тесты добавляют от
2.5 до 5.5 файла без remediation в продукте, а сужение до одного слоя обрывает цепочки
`Api → Application → Domain` и `Infrastructure → Application`, в которых и живёт
достижимость: в одном пилоте 138 из 152 файлов `Infrastructure` лежат в `Features/*`.

Обсуждались альтернативы:

- **Путь к бизнес-логике в `.harness.json`.** Это per-path исключение в tracked-файле,
  которые ADR-0032 и ADR-0042 уже убрали: агент, упёршийся в гейт, сдвинет границу, а не
  разорвёт ребро. Каждая правка пути меняет единицу измерения, и ratchet-бюджет перестаёт
  сравниваться со вчерашним.
- **Флаг включения тестов.** Значение `true` не даёт числа, по которому можно действовать;
  ADR-0042 уже решил, что связанность тестов, если понадобится, станет второй строкой
  бюджета, а не примесью к первой. Явная строка `false` в каждом конфиге — шум.
- **Граница из tracked `.csproj`.** Тестовый проект распознаётся по собственному XML:
  `Microsoft.NET.Test.Sdk`, xunit, NUnit, MSTest, TUnit в `PackageReference`,
  `IsTestProject`, `Sdk="MSTest.Sdk"`. Файл принадлежит ближайшему проекту вверх по
  дереву. Это та же линия, что в ADR-0033 и ADR-0041: граница читается из дерева,
  ридер tracked XML уже есть, MSBuild evaluation не нужна.

## Decision

1. **Область DSM без зоны — файлы вне тестовых проектов.** Когда `architecture` не
   применима или зона не найдена, `complexity.csharp` измеряет authored `.cs`, чей
   ближайший tracked проект не тестовый. Файл без проекта над собой считается продуктом.
   Репозиторий без единого тестового проекта по-прежнему измеряется целиком.
2. **Зона имеет приоритет.** Внутри `sliced-dotnet/1` область остаётся зоной ADR-0042;
   числа пилотов не меняются.
3. **Решение видно.** Строка `scope:` называет вынесенные тестовые проекты и число их
   файлов. `.csproj` входит в `Evidence` проверки по ADR-0026.
4. **Настроек нет.** Ни пути к бизнес-логике, ни флага тестов; `harness init --kind
   library` записывает бюджет уже по новой границе.
5. **Миграция.** Контракт `2.10.0`; маршрут `harness upgrade` описывает изменение.
   Бюджет остаётся валидным: в репозитории без зоны число только падает, и
   `harness budget update` при желании фиксирует улучшение.

## Consequences

### Positive

- Mean reach и core size доступны любому C#-репозиторию без принятия `sliced-dotnet/1`,
  и тесты не входят в знаменатель ни в одном режиме.
- Обход через конфиг по-прежнему невозможен физически: у проверки нет поля для границы.
- Ридер `.csproj` стал общим для семейств проверок вместо зависимости
  `Architecture → DotNet`.

### Negative / Risks

- Тестовый проект, чей маркер приходит только через `Directory.Build.props`, не
  распознаётся и остаётся в измерении; отчёт показывает это в `scope:`, а список маркеров
  придётся расширять по мере появления новых фреймворков.
- Бенчмарки, сэмплы и tooling без тестового маркера входят в продукт монолита; вынести их
  можно только физически, через тестовый проект или зону.
- Числа монолита и sliced-репозитория остаются несравнимыми между собой: граница разная,
  сравнение — только с собственной историей через бюджет.
