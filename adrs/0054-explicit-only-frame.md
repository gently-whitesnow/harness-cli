# ADR-0054: Рамка явная и только явная — контракт 3.0

## Status

Accepted. Уточняет [ADR-0017](0017-required-by-default.md) (раздел «Contract 2.0») и
[ADR-0035](0035-policy-switch-is-uniform.md): правило «каждая shipped-проверка перечислена
в `policy`, каждая ось — в `applicability`, каждая секция — в `settings`» заменено правилом
этого ADR. Значения policy и запрет адресного подавления из ADR-0035 действуют без изменений.

## Context

Контракт 2.0 требовал перечислить в `.harness.json` каждую shipped-проверку, каждую ось
applicability и каждую секцию settings. Так состояние всех проверок было видно в tracked-файле,
а новая проверка делала старый конфиг incomplete, пока владелец не выберет policy.

Пилот на Go-репозитории (~10k строк, стандартная раскладка `cmd/internal/pkg`, без C#)
показал цену этой формы: `harness init --kind application` записывал 31 policy-запись и секции
`comments.csharp`, `duplication.csharp`, `complexity.csharp`, а `harness check` печатал десять
строк `not applicable` про .NET и C# и падал на `architecture.sliced-dotnet.zone-shape`, потому
что зоны `Application/` в Go-репозитории нет. Файл говорил о стеке, которого у репозитория нет,
больше, чем о его собственном. Владелец принял модель EditorConfig: свойство, которое не написано,
не применяется.

Обсуждались две альтернативы. Оставить полный список, но давать `init` писать `applicable:
false` для необнаруженных языков — файл всё равно перечисляет чужие стеки, и каждая новая ось
дописывается во все репозитории. Или сделать отсутствующую проверку `required` по умолчанию,
как в ADR-0017 — тогда новая проверка молча включается в чужом репозитории, чего ADR-0032
сознательно избегал. Обе отвергнуты.

Главный риск явной-только модели — забытая фича: репозиторий добавил второй язык, а рамка
о нём молчит, и его проверки тихо остаются снаружи. Нужна защита, не возвращающая полный список.

## Decision

1. **Отсутствующее — снаружи рамки.** Проверка, которую `policy` не называет, не запускается,
   не является строкой отчёта и считается одной строкой `outside the frame`; `--only <id>`
   показывает её со словами «outside the frame». `harness.config` читается всегда. Ось,
   которой нет в `applicability`, не проверяется; язык — не исключение из этого правила.
2. **Названное — полное.** Проверка, названная в `policy`, несёт `required`, `advisory` или
   `off` и полную секцию `settings.<id>`, если её семейство (`comments`, `duplication`,
   `complexity`) читает настройки; скрытых числовых дефолтов нет. Секция для проверки, не
   названной в `policy`, — `Incomplete`: число, которое никто не применяет, хуже отсутствия.
   Policy-запись проверки, чья ось не объявлена в `applicability`, — `Incomplete`: рамка
   противоречит себе, и ридер называет, какую половину дописать. `settings.commits` нужна
   всегда: её читают команды `setup`, `commit-message` и `commits check`, а не проверка.
   `answers` обязательны для вопросов `frame.*`, названных в `policy`; `architecture` — как
   только названа хотя бы одна проверка `architecture.sliced-dotnet.*`.
3. **`harness init` пишет только обнаруженное.** Языки и .NET определяются по git-индексу
   через одну таблицу осей (`FrameAxis`: суффиксы языка, project-файлы .NET, вне generated-
   каталогов). Для необнаруженной оси не пишется ничего; `--languages <keys>` заменяет
   детекцию для CI. Вопрос application/library задаётся только при C# в индексе, потому что
   `sliced-dotnet/1` описывает C#-код; `.editorconfig` пишется только при .NET-проектах.
4. **`harness.coverage` защищает от забытой фичи.** Проверка группы `harness`, `required`
   из `init`: ось с tracked-источниками, у которой нет ни `applicable: true`, ни `applicable:
   false` с причиной, — blocking-находка с готовым JSON-фрагментом (applicability, settings с
   дефолтами контракта, policy) — тем самым, что написал бы `init`. Харнес tracked-файл не
   правит (ADR-0008); осознанный отказ выражается явным `applicable: false`.
5. **`harness upgrade` печатает маршрут от pin и только нужные секции.** Заметки релизов
   печатаются с версии, следующей за pin, а не всей историей; затем — фрагменты для
   обнаруженных осей без applicability и policy-записи shipped-проверок объявленных осей,
   которых policy не называет. Полный конфиг 2.17 — валидный 3.0: удалять ничего не нужно,
   а секции чужих стеков теперь можно убрать осознанно.
6. **Это контракт 3.0.** Меняется смысл отсутствующей записи, поэтому мажор.

## Consequences

### Positive

- На Go-пилоте после `init` файл содержит только `yaml`/`typescript`-секции, `frame.*`,
  `commits`, `docs.policy`, `harness.config` и `harness.coverage`; `check` не печатает `not
  applicable` для .NET и C#, а восемнадцать чужих проверок сведены в одну строку.
- Новая ось харнеса не требует правки всех репозиториев: там, где её источников нет, файл не
  меняется; там, где есть, `harness.coverage` и `upgrade` печатают готовый фрагмент.
- Одна таблица осей для `init`, `upgrade` и `harness.coverage`: язык, который один из них
  видит, не может быть забыт другим.

### Negative / Risks

- Состояние проверки больше не читается из одного файла целиком: чтобы узнать, что снаружи
  рамки, нужен отчёт (`outside the frame` в `--verbose` перечисляет идентификаторы). Это
  принятая цена за файл, описывающий только свой стек.
- Проверка объявленной оси, не названная в `policy`, снаружи рамки без находки: `coverage`
  судит оси, а не проверки. Защита — фрагмент в `harness upgrade` при каждом релизе.
- Детекция по суффиксам: репозиторий с одним vendored-файлом вне известных generated-каталогов
  получит находку `coverage`; ответ — явный `applicable: false` с причиной.
