# ADR-0039: Плотность X-контрактов сигнализирует о скрытой слоистости

## Status

Accepted. Дополняет cross-API правило `sliced-dotnet/1` из
[ADR-0033](0033-canonical-standard-over-declarations.md) неблокирующими сигналами.

## Context

Feature-Sliced Design 2.1 разрешает `@x`-нотацию только на слое entities: у FSD есть
вертикаль слоёв, и постоянные перекрёстные ссылки поднимают концепт на слой ниже. В
sliced-dotnet слой слайсов один, `Contracts/X/<Потребитель>` (и `Domain/<Слайс>/X/<Потребитель>`)
доступен каждому слайсу как last resort, и сам факт X-контракта проверкой уже
контролируется. Не контролировалась плотность: карта X-контрактов — единственный
структурный сигнал того, что внутри единственного слоя слайсов вырос неявный нижний слой.

Два паттерна наблюдаемы прямо по tracked-путям, без C#-графа. Взаимная пара — слайс A
публикует X-контракт для B, а B публикует X-контракт для A: ни один из них не ниже
другого, это одна возможность, разрезанная надвое, либо невыделенный общий концепт.
Fan-in — X-контракты слайса читают несколько разных соседей: слайс фактически работает
общим словарём, то есть нижним слоем, которым в sliced-dotnet являются `Domain` и `Shared`.

## Decision

1. Проверка `architecture.sliced-dotnet` строит по tracked-путям карту X-контрактов всех
   измерений слайса: `<Измерение>/Features/<Слайс>/Contracts/X/<Потребитель>/` и
   `Domain/<Слайс>/X/<Потребитель>/`; placeholder-файлы контрактом не считаются, имя
   потребителя разрешается тем же способом, что в правиле cross-API (включая
   `X/<Группа>/<Потребитель>`).
2. Взаимная пара — оба слайса публикуют X-контракты друг для друга — печатается один раз
   как advisory-observation `mutual-cross-api`: рассмотреть выделение общего концепта в
   `Domain`/`Shared` или слияние слайсов.
3. Слайс, чьи X-контракты адресованы 4 и более разным потребителям, получает
   advisory-observation `cross-api-fan-in`: слайс ведёт себя как нижний слой; общий концепт
   стоит опустить в `Domain` или `Shared`. Порог 4 выбран как минимальное число соседей,
   при котором «большинство соседей читает этот слайс» перестаёт быть парным исключением:
   один и два потребителя — штатный last resort, три — граница, где решение ещё локально.
4. Оба сигнала — observation-строки по прецеденту `insignificant-slice`, не `Finding`:
   remediation здесь архитектурное решение с ревью, а не локальная правка, поэтому по
   ADR-0002 сигнал не может быть blocking и не меняет код возврата ни при какой policy.

## Consequences

### Positive

- Скрытая слоистость становится видимой в каждом отчёте, пока каждый отдельный X-контракт
  всё ещё формально легален.
- Сигналы детерминированы по tracked-дереву и не зависят от читаемости C#-графа.

### Negative / Risks

- Карта строится по опубликованным контрактам, а не по фактическим импортам: X-контракт,
  который потребитель уже перестал читать, продолжает считаться. Осиротевший контракт —
  отдельная проблема формы, сигнал её не маскирует.
- Порог fan-in — соглашение; на репозиториях с очень большим числом слайсов четыре
  потребителя могут быть незначимой долей. Пересмотр порога — новым ADR.
