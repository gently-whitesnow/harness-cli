# ADR-0016: Версионированная рамка и явная инициализация

## Status

Accepted. Уточняет [ADR-0014](0014-frame-answers-are-self-reported.md) и заменяет часть
[ADR-0008](0008-the-harness-only-observes.md), запрещавшую харнесу писать `.harness.json`.
Обычный `check` остаётся только читающим; единственное исключение — явно вызванный `init`.

## Context

Список обязательных `answers` раньше брался прямо из всех frame-проверок текущего бинарника.
Добавление одного вопроса поэтому задним числом меняло контракт уже выпущенной версии, а
отсутствующий ответ обнулял весь прочитанный конфиг. В отчёте краснели все frame-проверки,
хотя исправить требовался один ключ.

Новому репозиторию также приходилось собирать конфиг из текста ошибки. Автоматически
созданные положительные ответы решили бы это ценой выдуманных self-reported утверждений:
харнес их не факт-чекает, и такая рамка сразу стала бы зелёной без участия владельца.

## Decision

`version` задаёт снимок всего контракта `.harness.json`. Число фиксирует набор frame-вопросов
этой версии; строка `"latest"` выбирает текущую версию запущенного бинарника. Каждый новый
frame-вопрос получает версию появления и повышает текущую версию контракта. Новый бинарник
продолжает читать поддерживаемые старые снимки, а вопросы из более новых версий показывает
как skipped. Будущая неизвестная версия оставляет весь запуск incomplete.

Ошибки известных `answers.<key>` локальны. Отсутствующий или malformed ответ делает
incomplete только соответствующий `frame.<key>`; остальные ответы, policy и settings
остаются пригодны. Нечитаемый JSON, неверная оболочка, неизвестные ключи и недостоверные
policy, settings или suppress остаются глобальными ошибками `harness.config`.

`harness init [path]` — явная opt-in команда, которая создаёт новый `.harness.json` в корне
Git-репозитория. По умолчанию она фиксирует текущую числовую версию; `--latest` выбирает
rolling-контракт. Команда не перезаписывает существующий файл, не добавляет его в Git и не
меняет иной контент.

Каждый созданный answer-key содержит пустой объект-placeholder. Поэтому первый `check`
намеренно красный и называет все нерешённые вопросы. Remediation предлагает агенту сначала
исследовать репозиторий и записать честный положительный, отрицательный или неприменимый
ответ. Если intent или applicability нельзя установить из evidence, агент спрашивает
владельца. Массовый suppress и выдуманный положительный ответ не являются инициализацией.
Осознанное отсутствие выражается `present: false` с причиной и даёт readiness gap;
`suppress` предназначен для адресных findings, а не для вопросов рамки.

## Consequences

### Positive

- Новый вопрос не ломает pinned-конфиги старого снимка.
- `latest` даёт осознанный способ сразу увидеть новый вопрос как одну actionable ошибку.
- Один неверный ответ больше не скрывает корректные независимые ответы.
- Начальная рамка перечисляет все поля, но не выдаёт догадки генератора за решение владельца.
- Агент получает следующий шаг из `check --verbose`, не размывая обычный компактный отчёт.

### Negative / Risks

- Бинарник должен хранить metadata версий старых вопросов, пока поддерживает старые снимки.
- `latest` требует согласованно обновлять CLI локально и в CI.
- После `init` репозиторий заведомо не проходит frame до явной настройки каждого ответа.
- `init` — узкое исключение из прежнего простого правила, что харнес только наблюдает.
