# ADR-0026: Проверка называет файлы, которые читает, и отчёт объясняет невидимые

## Status

Accepted. Уточняет [ADR-0004](0004-execution-plan-from-git-evidence.md) и
[ADR-0014](0014-frame-answers-are-self-reported.md): инвентарь репозитория остаётся
git-индексом, меняется только то, что отчёт умеет об этом сказать.

## Context

Инвентарь строится из `git ls-files --stage`, поэтому файл, лежащий на диске без `git add`,
для харнеса не существует. Принцип верен: untracked-файл не видят ни коллега, ни CI, и
доказательством он не является. Содержимое уже отслеживаемого файла при этом читается из
рабочего дерева, так что правка без стейджинга видна — расходится только новый файл.

Наблюдаемая цена всплыла при подключении харнеса к пилотному монорепозиторию.
`central-packages.dotnet` сообщает «has PackageReference items but no tracked
Directory.Packages.props». Автор создаёт `backend/Directory.Packages.props`, перезапускает
`check` — текст дословно тот же. После `git add` проверка зеленеет. По выводу «я не создал
файл» и «я создал, но не застейджил» неразличимы, а при подключении харнеса второй случай —
норма. То же формулируют `solution-format.dotnet` и `build-properties.dotnet`.

Обсуждались три выхода. Считать инвентарь обходом рабочего дерева с учётом `.gitignore` —
отклонено: сегодня untracked-файл может дать только ложное нарушение, локальный вердикт при
этом совпадает с CI; при обходе дерева он начал бы прятать нарушение — зелено локально,
красно в CI, — а локальные черновики стали бы субъектами blocking-проверок. Дописать
подсказку в текст каждой такой находки — заплатка в трёх местах, которая забудется в
четвёртой. Обходить файловую систему самостоятельно — отклонено: `.gitignore` со вложенными
файлами и отрицаниями честно реализует только сам Git.

Первая реализация несла искомые пути в самой находке необязательным полем. Владелец задачи
указал на её слабость: поле забывается молча, и следующая проверка потеряет диагностику.
Разбор показал, что поле вдобавок не достаёт до двух случаев без находки — незастейдженный
`.harness.json` после `init` (исход `Incomplete`) и незастейдженный `.csproj` (исход
`NotApplicable`), — а это самые первые шаги подключения.

## Decision

Проверка обязана назвать файлы, которые читает по имени и об отсутствии которых сообщает:
`IRepositoryCheck.Evidence` — член без реализации по умолчанию. Имя — либо имя файла, либо
`*.ext`, когда подошёл бы любой файл такой формы. Новая проверка не компилируется, пока не
ответит; «никаких» — тоже явный ответ. Это та же дисциплина, которой харнес требует от
репозитория: обязательный ответ на каждый вопрос рамки, включая отрицательный (ADR-0016,
ADR-0017).

Спросить инвентарь по имени можно только через контекст проверки: `context.Tracked(evidence)`
и `context.Nearest(evidence, path)`. Контекст знает, какая проверка выполняется, и отвечает
только на объявленное; запрос по необъявленному — исключение, то есть `Incomplete` с именем
проверки. Негативная фикстура, обязательная по [ADR-0002](0002-when-a-check-becomes-blocking.md),
ловит это в первом же прогоне. Литерал имени файла живёт в одном месте — в объявлении.

Движок после прогона собирает объявления тех проверок, которые оставили вопрос открытым
(находка, `Failed`, `Incomplete`, `ReadinessGap` или `NotApplicable`), и пересекает их с
ответом `git ls-files --others --exclude-standard -z`. Пересечение печатается в блоке git
evidence строкой `not in the index` с указанием `git add`. Проверка, исключённая из прогона
или объявленная неприменимой в конфиге, вопроса не задавала и в сбор не входит; чистый pass —
тоже. Поэтому вызов Git выполняется, только если что-то осталось необъяснённым.
`harness explain` печатает объявление, так что у него есть и читатель-человек.

Вердикт, коды возврата и тексты находок не меняются: untracked-файл по-прежнему не
доказательство. Меняется только диагностика, поэтому новых находок появиться не может и
`Since` этому изменению не нужен — инвариант ADR-0023 держится без гейта.

## Consequences

### Positive

- Диагностику нельзя потерять в следующей проверке: компилятор ловит «не ответил», а контекст
  и её собственные фикстуры — «прочитал необъявленное».
- Объявление живёт на проверке, а не на находке, поэтому подсказка работает и там, где
  находки нет вовсе: `.harness.json` после `init` и незастейдженный `.csproj` объяснились без
  единой строки в самих проверках.
- Объявление стало общим словарём: `explain` печатает его, ревью видит строкой диффа, а имя
  файла перестало дублироваться между вызовом поиска и текстом находки.
- Обычный прогон не платит ничего: все проверки прошли — второго вызова Git нет.

### Negative / Risks

- Подсказка теперь по имени, а не по точному пути: незастейдженный `Directory.Build.props` в
  другом каталоге будет назван, даже если находка про другой проект. Для подсказки это
  приемлемо, для вердикта было бы нет — вердикт её не читает.
- «Ответил не тем» ловится в рантайме, а не компилятором: проверка, читающая файл в обход
  контекста, останется незамеченной. Контекст закрывает поиск по имени, а не обход инвентаря;
  `docs.policy` судит весь Markdown и потому по-прежнему опирается на объявление.
- Каждая проверка получила обязательный член: 19 строк единовременно и одна строка на каждую
  будущую проверку. Это и есть цена того, что вопрос нельзя не задать.
- Вывод в неподготовленном репозитории стал на две строки длиннее. Компактный режим их
  печатает намеренно: именно там, где рамку только подключают, подсказка и нужна.
