# ADR-0008: Харнес наблюдает и ничего не изменяет

## Status

Accepted. Ядро решения — «харнес не правит tracked-контент, не ставит toolchain, не меняет
lockfile» — действует и распространяется на `.harness.json`: его харнес тоже не пишет.
Ограничения на форму запускаемой команды потеряли предмет с
[ADR-0011](0011-the-harness-does-not-run-the-repository-toolchain.md): харнес не запускает
toolchain репозитория вообще, поэтому исправляющую команду ему нечем вызвать.

## Context

В дизайн-сессии пользователь отверг `fix` как обязательную способность инструмента: CLI
должен сказать агенту, что не так, а агент — оценить и внести изменение. Переиспользуемые
quality checks живут в CLI; business cases и repository-specific architecture tests остаются
в репозитории. Автоматическое изменение production code и CI в v0 не входит.

Это ограничение существенно для делегирующих гейтов: `dotnet format`, Prettier и ESLint
имеют как проверяющие, так и исправляющие режимы, а package script может спрятать mutating
команду во вложенном script. Silent install также меняет dependency state и может обновить
lockfile, поэтому отсутствие toolchain или dependencies должно оставаться явным.

## Decision

Харнес не правит tracked-контент, не устанавливает toolchain и не меняет lockfile.

Отсюда ограничения на запуск: `dotnet format` вызывается с `--verify-no-changes`; при
tracked lock-файле восстановление идёт с `-p:RestoreLockedMode=true`; web-гейт берёт скрипт,
который проверяет, а не исправляет. Скрипт с `--write`, `--fix`, `--apply` — readiness gap,
а не запуск. Скрипт с именем, которое в экосистеме принято за исправляющее (`format`),
запускается, только если команда явно заявляет режим проверки (`--check`, `--verify`,
`--list-different`, `--dry-run`). Команда раскрывается транзитивно, поэтому
`"format": "npm run format:fix"` не проходит через это ограничение вложенным скриптом.

Репозиторий с объявленными, но не установленными зависимостями даёт `Incomplete` с просьбой
установить их самому.

## Consequences

### Positive

- Приёмочные fixtures сравнивают tracked Git state до и после `check`; изменение самим
  харнесом считается нарушением внешнего контракта.
- Правило проверяется на реальном репозитории: в services-platform выбран `format:check`,
  а не `format`, хотя объявлены оба.
- Один и тот же цикл остаётся явным: харнес наблюдает, агент исправляет, следующий прогон
  проверяет новое состояние.

### Negative / Risks

- Веб-гейты не работают, пока зависимости не установлены: на services-platform все пять
  дали `Incomplete` до `pnpm install`.
- Репозиторий, у которого есть только исправляющий вариант команды, не проверяется вовсе —
  это readiness gap, и закрыть его может только сам репозиторий.
- Build и test toolchains всё ещё могут создавать conventional ignored outputs; гарантия
  относится к tracked source, policy и lockfiles, а не к побайтовой неизменности каталога.
